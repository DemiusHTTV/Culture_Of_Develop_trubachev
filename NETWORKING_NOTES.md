# Взаимодействие микросервисов: Сетевые особенности Docker

Главное правило при работе с сетью: `127.0.0.1` (или `localhost`) означает "текущую машину", на которой выполняется код. В контексте Docker эта концепция часто вызывает путаницу. Рассмотрим 4 основных сценария:

## 1. Локальный запуск с 127.0.0.1 (без Docker)
Когда вы запускаете сервисы (например, через `poetry run uvicorn`) прямо на своей ОС (Mac, Windows, Linux), все они делят один и тот же сетевой интерфейс (`localhost`). 
- **Как это работает:** `order-service` отправляет запрос на `http://127.0.0.1:8001`. Этот запрос не выходит за пределы вашей машины и успешно доставляется локально запущенному `product-service`.
- **Итог:** Всё работает, потому что `localhost` для обоих сервисов — это ваш компьютер.

## 2. Неудачный запуск контейнера с 127.0.0.1
Что произойдет, если запустить сервисы внутри Docker-контейнеров, но в коде `order-service` оставить URL `http://127.0.0.1:8001`?
- **Как это работает:** Внутри контейнера с `order-service` `127.0.0.1` означает *сам этот контейнер*, а не ваш компьютер и не контейнер с `product-service`. 
- **Итог:** `order-service` попытается найти `product-service` на порту 8001 внутри себя самого. Он получит ошибку `Connection Refused` (или 503/502), так как там ничего не запущено. Запрос уходит "в никуда".

## 3. Успешное взаимодействие контейнеров через имена сервисов (Docker Compose)
Чтобы контейнеры могли общаться, мы помещаем их в общую виртуальную сеть (например, `app-network` в нашем `docker-compose.yml`).
- **Как это работает:** Docker имеет встроенный DNS-сервер. Когда `order-service` делает запрос на `http://product-service:8000`, Docker автоматически переводит имя `product-service` во внутренний IP-адрес нужного контейнера в этой сети. 
- **Итог:** Запрос успешно доходит до нужного контейнера. Обратите внимание, что мы стучимся на внутренний порт контейнера (8000), а не на порт хоста (8001), потому что трафик не выходит наружу.

## 4. Взаимодействие через хост с использованием host.docker.internal (Необязательно)
Иногда контейнеру нужно достучаться до сервиса, который запущен на вашем основном компьютере (хосте), а не в другом контейнере (например, локальная база данных, которую вы еще не перенесли в Docker).
- **Как это работает:** Использовать `127.0.0.1` из контейнера нельзя (см. пункт 2). Вместо этого в Docker Desktop (Mac/Windows) предусмотрен специальный DNS-адрес `host.docker.internal`. Он всегда резолвится в IP-адрес вашей хост-машины.
- **Итог:** Если ваш сервис запущен локально (без Docker) на порту 8001, контейнер сможет к нему обратиться по адресу `http://host.docker.internal:8001`. Это полезный костыль для локальной разработки, но в production-окружениях (например, на Linux) он работает иначе или вообще отключен.
